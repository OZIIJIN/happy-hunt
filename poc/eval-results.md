# 아이템 추출 POC — 모델 비교 평가 결과

`poc/run-eval.ts`로 `poc/test-memos.ts`의 정답 케이스를 로컬 LLM(Ollama)에 돌려
아이템 매치율/속도/엣지케이스 처리를 비교한 기록.

## 테스트 케이스 구성

`test-memos.ts`는 카테고리 순서대로 배열돼 있다 (총 100개):

| 구간 | 카테고리 | 케이스 수 |
| --- | --- | --- |
| 1~18 | 음식 | 18 |
| 19~33 | 장소 | 15 |
| 34~48 | 자연 | 15 |
| 49~63 | 사물 | 15 |
| 64~78 | 사람_동물 | 15 |
| 79~90 | 활동 | 12 |
| 91~100 | 엣지케이스 (정답 없음, 빈 배열이 정답) | 10 |

케이스를 앞에서부터 N개 잘라 실행하므로, N=50이면 음식/장소/자연(+사물 앞부분)만
커버하고, N=100이어야 사물/사람_동물/활동/엣지케이스까지 전부 포함된다.

## 51~100번 구간(사물/사람_동물/활동/엣지케이스)만 따로 보면

50개 결과와 100개 결과의 매치 개수를 직접 비교하면, 뒤쪽 절반에서 사실상 정답을
거의 못 맞혔다는 게 드러난다.

| 모델 | 50케이스 매치 | 100케이스 매치 | 51~100 구간에서 늘어난 매치 |
| --- | --- | --- | --- |
| qwen3:8b | 45/64 | 45/106 | **0/42** |
| qwen2.5:7b | 40/64 | 40/107 | **0/43** |
| gemma3:4b | 45/64 | 49/107 | 4/43 |

`qwen3:8b`와 `qwen2.5:7b`는 51번 이후 케이스에서 새로 맞힌 정답이 0개다.

### 원인

1. **활동 카테고리(79~90)** — 정답이 "자전거", "요가", "클라이밍" 같은 활동
   자체인데, 모델들은 그 옆의 감각적 명사("바람", "정상의 바람", "유연한 몸")를
   대신 추출한다. 시스템 프롬프트가 "구체적 사물/음식/장소/자연 요소를 우선"하라고
   지시하고 있어, 활동보다 자연/사물 쪽 답을 유도하는 것으로 보인다.
2. **엣지케이스(91~100)** — 정답은 빈 배열(아이템 없음)이어야 하는데, 모델이
   "베개", "편안함", "따뜻한 커피" 등을 억지로 만들어낸다. `qwen2.5:7b`는 10개
   전부 실패(0/10) — 과다 추출 경향이 뚜렷하다.
3. **사물/사람_동물(49~78)** — 일부 실패가 있지만 위 두 카테고리만큼 극단적이지
   않음.

즉 매치율 하락은 모델 성능이 갑자기 나빠진 게 아니라, 테스트셋 뒷부분(활동·
엣지케이스)이 현재 프롬프트/카테고리 설계상 구조적으로 더 어려운 유형이기
때문이다.

## 종합

- 정확도·속도·엣지케이스 처리 균형에서 **`gemma3:4b`가 가장 유력한 후보**.
  다른 모델과 매치율이 비슷하거나 더 높으면서, `qwen3:8b` 대비 10배 이상 빠르고
  로컬 자원도 덜 씀(파라미터 수 4B).
- 다음 개선 방향(향후 과제):
  - 시스템 프롬프트에 "활동"도 명시적으로 아이템 후보에 포함하도록 규칙 보강.
  - 엣지케이스 판별 기준(언제 빈 배열을 반환해야 하는지)을 프롬프트에 더 명확히
    명시하거나 few-shot 예시 추가.
  - `qwen3:8b`에서 발생한 네트워크 에러(`fetch failed`)에 대한 재시도 로직 추가
    (현재 `extractWithRetry`는 스키마 검증 실패만 재시도하고 fetch 자체의 실패는
    재시도하지 않음).

## v0.2 프롬프트(few-shot 롤백) + 모델 6개 확장 비교 (2026-09-22, 언로드 버그 수정 이후)

v0.3(few-shot 추가, 커밋 `f8ce38e`)은 위 "few-shot 예시" 롤백 기록대로 다시
v0.2로 복귀했다(커밋 `57f37a1` "프롬프트 v0.2로 복귀"). 즉 이 절의 평가는
few-shot이 빠진 v0.2 프롬프트 기준이다. 여기에 `gemma4:e4b`를 새 후보로 추가한
뒤, 위 100개 케이스 전체로 6개 모델(`qwen3:8b`, `qwen2.5:7b`, `qwen2.5:3b`,
`gemma3:4b`, `gemma4:e4b`, `llama3.2:3b`)을 다시 비교했다. 그 과정에서 발견한
인프라 버그와, "사람을 아이템으로 잘못 뽑는" 문제를 모델 전체로 넓혀 조사한
결과를 함께 기록한다.

### 사전 조사: `fetch failed` 에러의 원인

3모델(`gemma3:4b`, `gemma4:e4b`, `qwen3:8b`) 순차 비교 중 `qwen3:8b` 구간에서
`fetch failed` 에러가 반복 발생했다. `/opt/homebrew/var/log/ollama.log`를 보면
원인이 명확했다:

- `run-eval.ts`는 모델을 바꿀 때 이전 모델을 명시적으로 내리지 않는다. ollama는
  기본적으로 유휴 상태가 일정 시간 지나야 모델을 자동 언로드하는데, 모델 하나당
  케이스를 연달아 처리하는 동안은 계속 "활성" 상태라 다음 모델로 넘어가도 이전
  모델이 메모리에 남아있다.
- 이 머신은 통합 메모리 24GB 중 ollama 없이도 이미 23GB가 다른 프로세스(VS Code,
  Notion, Claude Code 세션들)에 쓰이고 있어 여유가 거의 없다(415MB).
- 두세 모델이 동시에 적재되면(로그상 `loaded runners count=2`, 여유 메모리
  2.8GiB까지 하락) 추론이 극단적으로 느려지고, Node의 기본 fetch 타임아웃(5분)에
  걸려 요청이 끊긴다. 로그의 `500 | 5m1s` 패턴이 그 증거.

**조치**: `run-eval.ts`에 `unloadModel()`을 추가해 모델 전환 시 `keep_alive: 0`으로
명시적으로 이전 모델을 내리도록 수정. 또한 프로세스가 중간에 죽어도 완료된 모델
결과는 보존되도록, 모델별 리포트를 전체 루프가 끝난 뒤가 아니라 각 모델이 끝나는
즉시 출력하도록 변경했다.

이 수정으로 모델 간 스택으로 인한 `fetch failed`는 사라졌지만, `qwen3:8b`는 단독
실행 중에도 이 머신의 메모리 한계 때문에 이따금 같은 에러가 남아있다(아래 표의
에러 5건) — 이건 코드로 해결되는 문제가 아니라 머신 리소스 한계로 보인다.

강제했음에도 마크다운 코드펜스로 감싼 **문자열 배열**을 내는 패턴이었다:

```json
{"items": ["창가", "라떼", "책"]}
```

`{name, category, evidence, visual_description, uniqueness}` 객체가 아니라 문자열이라
Zod 검증에서 항상 실패한다. 원인은 아직 미규명 — ollama의 구조화 출력 강제가 이
모델에서 간헐적으로 안 먹히는 것으로 추정된다.

### "사람 오분류" 문제를 모델 전체로 확인

케이스 64~78번 구간(사람만 등장, 정답은 빈 배열인 7개)과 91~100번 구간(사람도
안 나오는 순수 "특별한 일 없는 하루" 엣지케이스 10개)을 나눠서 보면, 엣지케이스
통과율 하나로 뭉뚱그려졌던 문제가 훨씬 선명하게 드러난다.

| 모델 | 사람만 등장 (7개 중 통과) | 순수 엣지케이스 (10개 중 통과) |
| --- | --- | --- |
| qwen3:8b | 6/7 | 9/10 |
| qwen2.5:7b | **0/7** | 10/10 |
| qwen2.5:3b | **0/7** | 10/10 |
| gemma3:4b | 1/7 | 7/10 |
| gemma4:e4b | 6/7 | 10/10 |
| llama3.2:3b | **0/7** | 6/10 |

**중요한 발견**: "사람은 어떤 카테고리로도 뽑지 않는다"는 규칙(AGENTS.md
"사람_동물 분리" 결정 반영)을 **`qwen2.5:7b`, `qwen2.5:3b`, `llama3.2:3b`는
사실상 하나도 못 지킨다(0/7)**. 반면 순수 엣지케이스(사람 자체가 안 나오는
경우)는 거의 다 잘 거른다. 즉 "엣지케이스 처리를 잘하는 모델"이라는 인상이,
실은 "사람만 배제하는 규칙은 완전히 무시하지만 다른 무(無)아이템 케이스는
잘 거르는 것"으로 위장된 경우가 있다는 뜻이다. 이 규칙을 안정적으로 지키는
건 지금까지 테스트한 것 중 `gemma4:e4b`와 `qwen3:8b`(둘 다 상대적으로
큰 모델)뿐이었다.

### 왜 그렇게 뽑았는지 모델에게 직접 물어본 결과

`gemma3:4b`가 사람을 아이템으로 뽑을 때 실제로 어떤 카테고리를 붙이는지, 그리고
같은 대화 turn에서 "왜 그렇게 판단했는지" 되물어본 결과:

- 카테고리 선택이 사실상 무작위였다: "친구" → `장소`, "친구" → `음식`,
  "아기 조카" → `자연`, "손"(할머니 손을 잡은 것) → `장소`. 스키마의 7개 카테고리
  enum 중 "사람"에 해당하는 값이 없어서, 사람을 뽑기로 한 순간 아무 칸에나
  끼워 맞추는 것으로 보인다.
- 후속 질문("왜 그렇게 뽑았어?")에 대한 답변은 **자기 출력과 모순되는 경우가
  있었다** — 케이스 72번("아빠가 서툰 요리를 해주셔서...")에서 1차 JSON 출력은
  `"요리"`(활동) 하나뿐이고 "아빠"는 넣지도 않았는데, 설명에서는 "아빠라는 단어가
  등장했기 때문에 아빠를 아이템으로 뽑았습니다"라고 하지도 않은 행동을 서술한 뒤
  "하지만 규칙에 따라 넣지 않았습니다"라고 자기모순을 냈다.
- 결론: 소형 로컬 모델에게 "왜 그렇게 판단했어?"라고 되묻는 건 실제 내부 판단
  근거를 읽어오는 방법이 아니다. 그 순간 또 한 번 그럴듯한 텍스트를 생성하는
  것뿐이라, 1차 출력과 모순되는 설명도 태연하게 낸다. 다만 여러 설명에서 "이
  사람이 그 순간의 핵심 존재라서 뽑았다"는 뉘앙스가 반복된 건, 사람이 문장에서
  감정적으로 두드러진 주어라 모델이 억지로 대표하려는 경향이라는 가설과는
  방향이 일치한다.

### 종합 결론

- 단일 지표(매치율/엣지케이스 통과율)만 보면 안 된다 — 특히 "사람 제외" 규칙
  준수 여부를 반드시 따로 확인해야 한다.
- 에러 0건 + 사람 규칙까지 지키는 모델은 이번 비교에 없었다. `gemma4:e4b`가
  사람 규칙과 순수 엣지케이스 모두 제일 잘 지키지만 스키마 위반 18%가 걸리고,
  `qwen3:8b`는 비슷하게 좋지만 너무 느리고(50.8s/케이스) 잔여 네트워크 에러가
  있다.
- `qwen2.5:7b`/`qwen2.5:3b`/`llama3.2:3b`는 에러 없이 안정적이지만 "사람 오분류"
