# Final Selector v0.5.2 — 500개 테스트셋 최종 검증

## 1. 실험 목적

100개 테스트에서 선택한 Final Selector v0.5.2가 더 큰 테스트셋에서도 동일한 동작 특성을 유지하는지 확인하고, 추가 프롬프트 튜닝 없이 Final Selector 실험을 종료할 수 있는지 판단했다.

종료 기준은 다음 세 가지다.

1. Selector 미적용 대비 FP가 명확하게 감소하는가
2. 의미 있는 아이템을 과도하게 제거하지 않는가
3. 100개 테스트에서 발견하지 못한 새로운 대규모 회귀가 발생하지 않는가

### 고정 조건

- Final Selector: v0.5.2
- commit: `600be40`
- model: `gemma3:4b-it-q8_0`
- temperature 및 inference 설정 동일
- Stage 1 / 2 / 2.5 / 3 프롬프트 및 로직 변경 없음
- 실행:
  `node --experimental-strip-types poc/run-eval.ts gemma3:4b-it-q8_0 999`
- 로그:
  `poc/eval-run-500-final-selector-v0.5.2.log`

500개 중 앞 100개 결과는 기존 100개 v0.5.2 실행과 완전히 동일했다.

## 2. 핵심 결과

500개에서는 별도의 Selector-off 실행을 하지 않았기 때문에, **동일 실행에서 Final Selector에 들어가기 직전의 후보를 Selector 미적용 결과(counterfactual)** 로 사용했다.

| 지표 | Selector 적용 전 | v0.5.2 | 변화 |
|---|---:|---:|---:|
| TP / FP / FN | 485 / 442 / 77 | 432 / 201 / 130 | FP −241, TP −53 |
| Precision | 52.3% | **68.2%** | **+15.9%p** |
| Recall | 86.3% | **76.9%** | −9.4%p |
| F1 | 65.1% | **72.3%** | **+7.2%p** |
| Edge-case Pass | 59/68 (86.8%) | 59/68 (86.8%) | 동일 |

Final Selector는 후보 960개 중 640개를 남겨 Keep Rate 66.7%를 기록했고, 입력에 도달한 expected 485개 중 432개를 유지해 Expected Preservation 89.1%를 기록했다. 동시에 expected와 매칭되지 않은 후보 442개 중 241개를 제거했다.

### 100개 결과와 비교

| 지표 | 100개 | 500개 |
|---|---:|---:|
| Precision 변화 | 48.8 → 68.2 | 52.3 → 68.2 |
| Recall 변화 | 81.3 → 76.0 | 86.3 → 76.9 |
| F1 변화 | 60.9 → 71.9 | 65.1 → 72.3 |
| FP 감소율 | −58.5% | −54.5% |
| Keep Rate | 66.7% | 66.7% |
| Expected Preservation | 93.6% | 89.1% |

Precision과 Keep Rate가 거의 동일하게 재현됐고 FP도 50% 이상 감소했다.

따라서 **Final Selector의 기본 필터링 강도와 FP 제거 효과는 100개에서 500개로 확장해도 유지됐다.**

## 3. Selector가 실제로 수행한 작업

500개에서 Selector는 다음과 같이 동작했다.

| 지표 | 값 |
|---|---:|
| Input | 960 |
| Selected | 640 |
| Removed | 320 |
| Keep Rate | 66.7% |
| Expected Preservation | 432/485 = 89.1% |
| Non-expected Removal | 241/442 = 54.5% |

Removed 320개는 다음과 같이 구성된다.

- expected 제거: 53개
- non-expected 제거: 241개
- 동일 expected에 중복 매칭되던 후보 제거: 26개

즉 Final Selector는 FP 제거뿐 아니라 **동일한 의미를 중복해서 표현하던 후보도 정리했다.**

Selector 입력에서는 하나의 expected에 여러 후보가 매칭된 중복 후보가 33개였지만, Selector 이후에는 7개로 줄었다.

이 효과는 현재 Precision / Recall / F1에는 직접 반영되지 않는다.

## 5. Expected 제거 53건의 제품 관점 재평가

Expected Preservation 89.1%는 **expected에 포함된 항목이 제거됐는지만 판단하는 자동 지표**다.

하지만 Happy-Hunt의 실제 목적은 expected 문자열을 모두 보존하는 것이 아니라,

> 사용자가 나중에 아이템을 봤을 때 행복했던 순간을 충분히 떠올릴 수 있는 수집 아이템을 남기는 것

이다.

따라서 Selector가 제거한 expected 53건을 `원문 + 최종 아이템` 기준으로 다시 평가했다. 로그상 Selector가 제거한 expected는 총 53개다.

### 제품 관점 판정

| 판정 | 건수 | 비율 |
|---|---:|---:|
| **실제 제품 손실** | **17** | **32.1%** |
| 허용 가능한 대체 | 25 | 47.2% |
| 제거가 더 적절함 | 11 | 20.8% |
| 합계 | 53 | 100% |

즉 자동 평가에서는 53개가 모두 손실로 계산되지만, 제품 관점에서는 **36건(67.9%)은 최종 경험 품질을 실제로 악화시킨 손실이라고 보기 어려웠다.**

### 5.1 활동 제거: 좋은 대체와 나쁜 대체

ACTIVITY가 제거됐다고 해서 항상 제품 손실인 것은 아니었다.

#### 허용 가능한 대체

- 뜨개질 → 목도리
- 피아노 연주 → 피아노
- 기타 연주 → 기타
- 도예 → 그릇 / 머그컵
- 수영 → 수영장
- 피크닉 → 공원 + 딸기 + 샌드위치

활동 자체는 사라졌지만 **그 활동을 떠올릴 수 있는 대표적인 오브젝트나 결과물**이 남아 있다.

Happy-Hunt가 활동 자체를 문자 그대로 보관하는 서비스가 아니라 기억을 아이콘으로 수집하는 서비스라면, 이런 변환은 오히려 자연스럽다.

반면 다음은 실제 손실로 판단했다.

#### 실제 손실

- 게임 → 판 / 스테이지
- 독서 → 챕터
- 등산 → 정상
- 서핑 → 파도

이 경우 남은 후보는 활동의 대표 오브젝트라기보다 **문장에서 함께 등장한 파편적인 요소**다.

예를 들어 `목도리`는 뜨개질 경험을 충분히 떠올리게 하지만, `챕터` 하나만으로는 독서 경험을 제대로 표현하기 어렵다.

따라서 남은 한계는 단순히 **ACTIVITY를 많이 제거한다**는 것이 아니라,

> **활동을 의미 있는 대표 오브젝트로 압축한 경우와, 활동 의미를 잃고 약한 주변 요소만 남긴 경우를 구분하지 못한다는 것**

이다.

### 5.2 장소 제거: 배경과 경험의 정체성

장소 역시 제거 자체가 항상 문제는 아니었다.

예를 들어:

- 공원 + 라떼 + 책 → 공원 제거
- 산책로 + 강아지 + 노을 → 산책로 제거
- 테라스 + 파스타 + 참새 → 테라스 제거

에서는 장소를 빼더라도 행복했던 순간의 핵심 의미가 충분히 유지된다.

반면 다음 장소들은 실제 손실로 판단했다.

- 아쿠아리움
- 수목원
- 미술관
- 사찰
- 캠퍼스
- 항구
- 공항

이들은 단순 위치가 아니라 **경험의 종류 자체를 정의하는 장소**다.

예를 들어:

`아쿠아리움에서 물고기를 봄`

에서 아쿠아리움을 제거하고 `물고기`만 남기면 단순히 물고기를 본 경험과 구별하기 어려워진다.

따라서 장소에 대한 남은 한계 역시:

> PLACE를 제거한다는 것 자체가 아니라, **단순 배경 장소와 기억의 정체성을 만드는 장소를 안정적으로 구분하지 못한다는 것**

이다.

### 5.3 실제 손실의 구성

제품 관점에서 실제 손실로 판단한 17건은 다음과 같이 분포했다.

| 유형 | 건수 |
|---|---:|
| PLACE | 7 |
| ACTIVITY | 6 |
| OBJECT | 4 |
| 합계 | 17 |

자동 Expected Preservation은 432/485 = 89.1%지만, 제품 관점에서 실제 손실로 판단한 것은 17/485 = 3.5%였다.

따라서 참고용으로 실제 제품 의미가 유지된 비율을 계산하면:

**(485 − 17) / 485 = 약 96.5%**

가 된다.

단, 이 값은 자동 지표가 아니라 **LLM-as-a-Judge 기반 제품 관점 재평가 결과**이므로 `Expected Preservation`을 대체하는 공식 지표로 사용하지 않고 보조 해석으로만 사용한다.

## 6. Edge / Schema / Latency

### Edge case

Edge-case Pass Rate는 Selector 적용 전후 모두 59/68 = 86.8%로 동일했다.

실패한 9건은 흙, 여행지, 개, 이야기, 안아주다, 공기, 차, 뒹굴기, 움직임 등으로 모두 Selector 이전 단계에서 만들어진 후보였다.

Final Selector가 새로운 edge failure를 만들지는 않았지만, 이미 들어온 잘못된 후보를 완전히 제거하지도 못했다.

### Schema

- Stage 1: 500/500
- Stage 2: 467/467
- Stage 2.5: 234/234
- Final Selector: 431/431
- Stage 3: 429/429
- invalid ID: 0
- duplicate ID: 0
- 전체 2,061회 호출 실패: 0
- retry: 0

500개에서도 Structured Output 및 Selector ID 인터페이스는 안정적으로 동작했다.

### Latency

- Final Selector p50: 3,256ms
- Final Selector p95: 3,558ms
- Total p50: 19,746ms

100개의 Final Selector p50 3,177ms와 큰 차이가 없었다.

실행 도중 머신 slowdown이 발생해 avg / max는 왜곡됐기 때문에 p50 / p95를 기준으로 판단한다.

## 8. 현재 v0.5.2 성능 평가

500개 검증 결과를 기준으로 현재 Final Selector v0.5.2는 다음과 같이 평가할 수 있다.

> **FP를 절반 이상 제거하면서 의미 있는 아이템 대부분을 유지하고, 100개에서 확인한 동작 특성을 500개에서도 재현한 MVP 적용 가능 수준의 Final Selector**

정량적으로는 Selector 적용 전 대비:

- FP: 442 → 201, **54.5% 감소**
- Precision: 52.3% → **68.2% (+15.9%p)**
- Recall: 86.3% → **76.9% (-9.4%p)**
- F1: 65.1% → **72.3% (+7.2%p)**
- Expected Preservation: **89.1%**
- Keep Rate: **66.7%**
- Final Selector Schema 성공률: **100%**
- 새로운 실패 유형: 없음

즉 모든 후보를 최대한 보존하는 방식이 아니라, 일부 Recall을 희생하는 대신 불필요한 후보를 적극적으로 제거해 **사용자에게 보여주는 최종 아이템 집합의 정밀도를 높이는 방향**으로 동작한다.

또한 100개와 500개에서 Keep Rate가 모두 66.7%였고, FP 감소율도 각각 58.5%, 54.5%로 유사했다.

따라서 100개 테스트에서 관찰한 성능이 특정 데이터에 우연히 맞은 결과가 아니라, **현재 프롬프트가 가지는 일관된 필터링 특성**으로 판단할 수 있다.

### 자동 지표와 실제 제품 품질의 차이

자동 Expected Preservation은 432/485 = 89.1%로, Selector가 expected 53개를 제거한 것으로 계산한다.

하지만 제거된 53건을 원문과 최종 아이템을 기준으로 다시 평가한 결과:

| 판정 | 건수 | 비율 |
|---|---:|---:|
| 실제 제품 손실 | 17 | 32.1% |
| 허용 가능한 대체 | 25 | 47.2% |
| 제거가 더 적절함 | 11 | 20.8% |

53건 중 36건은 대표 오브젝트가 기존 활동을 충분히 대신하거나, 최종 기억에서 중요도가 낮은 배경 요소가 제거된 경우였다.

예를 들어:

- 뜨개질 → 목도리
- 피아노 연주 → 피아노
- 도예 → 그릇 / 머그컵

처럼 활동이 직접 남지 않더라도 해당 경험을 떠올릴 수 있는 수집 가능한 오브젝트가 남은 경우는 Happy-Hunt의 제품 방향과 부합한다.

반대로 다음과 같은 경우는 실제 품질 손실로 판단했다.

- 게임 → 판 / 스테이지
- 독서 → 챕터
- 등산 → 정상
- 서핑 → 파도

이는 활동의 대표 아이템으로 압축된 것이 아니라, 활동의 의미를 잃고 문장의 일부 요소만 남은 경우다.

PLACE 역시 동일하다.

- 공원 + 라떼 + 책 → 공원 제거
- 테라스 + 파스타 + 참새 → 테라스 제거

와 같이 장소를 빼도 장면의 의미가 유지되는 경우가 있는 반면,

- 아쿠아리움
- 미술관
- 공항
- 항구

처럼 장소 자체가 경험의 성격을 정의하는 경우도 존재했다.

따라서 현재 Final Selector의 남은 한계는 단순히 Recall이 낮다는 것이 아니라 다음 두 가지로 구체화할 수 있다.

1. **ACTIVITY를 의미 있는 대표 오브젝트로 압축한 경우와, 의미가 약한 주변 요소만 남긴 경우를 안정적으로 구분하지 못함**
2. **단순 배경 PLACE와 경험의 정체성을 구성하는 PLACE를 안정적으로 구분하지 못함**

제품 관점 재평가에서 실제 손실로 판단한 것은 17/485 = 3.5%였다.

이를 단순 참고값으로 환산하면 약 96.5%의 입력 expected가 제품 의미를 유지했다고 볼 수 있다.

단, 이 값은 자동 평가 지표가 아니라 LLM-as-a-Judge를 통한 제품 관점 보조 분석 결과이므로 공식 Expected Preservation을 대체하지 않는다.

---

## 9. 최종 판단

### Final Selector v0.5.2를 현재 MVP용 최종 버전으로 고정한다.

500개 검증에서 다음을 확인했다.

- FP **54.5% 감소**
- Precision **+15.9%p**
- F1 **+7.2%p**
- Keep Rate **66.7% 재현**
- Schema 성공률 **100%**
- 100개에서 없던 새로운 실패 유형 없음
- 단순 카테고리 구간에서는 expected **99.6% 보존**
- 자동 Preservation 하락의 대부분은 활동·복합 문장에서 발생한 기존 판단 패턴의 확대

Expected Preservation은 100개 93.6%에서 500개 89.1%로 감소했지만, 제거된 expected 53건을 제품 관점에서 분석한 결과 실제 품질 손실로 판단한 것은 17건이었다.

나머지는 대표 오브젝트가 경험을 대신 표현하거나, 최종 수집 아이템으로서 중요도가 낮은 배경 요소를 제거한 경우였다.

따라서 현재 성능은 **완성된 파이프라인이라고 보기는 어렵지만, Happy-Hunt의 핵심 MVP 흐름에 적용하고 실제 사용자 경험을 검증하기에는 충분한 수준**으로 판단한다.

남아 있는 ACTIVITY / PLACE 문제를 해결하기 위해 Final Selector에 추가 예외 규칙이나 few-shot을 넣는 것은 중단한다.

v0.5.1 실험에서 확인했듯이 4B 모델에 규칙을 계속 추가하면 특정 문제를 개선하는 대신 다른 후보의 FP 증가나 판단 경계 이동이 발생할 가능성이 있기 때문이다.

따라서 Final Selector는 **v0.5.2로 freeze하고 현재 POC 단계의 실험을 종료한다.**

## 10. 후속 단계

### 10.1 1순위 — MVP 앱 구현

다음 단계에서는 파이프라인 자체의 정확도를 더 높이는 작업보다 **현재 v0.5.2 파이프라인을 실제 Happy-Hunt MVP에 연결하는 작업을 우선한다.**

현재 POC를 통해 다음은 이미 확인했다.

- 메모에서 후보를 높은 Recall로 추출할 수 있음
- 의미 카테고리를 부여할 수 있음
- ACTIVITY 후보에 별도 수집성 판단을 적용할 수 있음
- Final Selector를 통해 불필요한 후보를 절반 이상 줄일 수 있음
- 500개에서도 동일한 필터링 특성이 재현됨
- Structured Output 인터페이스가 안정적으로 동작함

따라서 현재 단계에서 더 중요한 질문은:

> **“분류 정확도를 몇 % 더 올릴 수 있는가?”**

보다

> **“이 정도 품질의 아이템을 실제 앱에서 제공했을 때 사용자가 수집 경험을 가치 있게 느끼는가?”**

이다.

MVP에서는 우선 다음 전체 사용자 흐름을 구현한다.

```text
행복한 순간 기록
→ 아이템 추출 파이프라인 실행
→ 최종 아이템 지급
→ 아이템 이미지/아이콘 표시
→ 컬렉션에 저장
→ 사용자가 과거 행복 아이템을 다시 확인
```

이 단계에서는 현재 Stage 1 → Stage 2 → Stage 2.5 → Final Selector v0.5.2 → Stage 3 파이프라인을 그대로 사용한다.

### 10.2 MVP에서 파이프라인 품질 관측

MVP 구현 시 이후 품질 개선에 사용할 수 있도록 최소한 다음 정보를 남긴다.

- 원본 memo
- Stage 1 candidates
- Stage 2 category
- Stage 2.5 결과
- Final Selector 입력 / 선택 / 제거 후보
- 최종 지급 item

가능하다면 실제 사용자 행동도 이후 품질 지표로 활용한다.

예:

- 지급된 아이템을 유지했는가
- 사용자가 아이템을 삭제했는가
- 재생성을 요청했는가
- 특정 아이템을 컬렉션에 계속 보관하는가
- 어떤 카테고리의 아이템을 선호하는가

현재 테스트셋의 expected는 사전에 정의한 정답이지만, 실제 앱에서 발생하는 사용자 행동은 **어떤 아이템이 실제로 가치 있는지를 판단할 수 있는 제품 데이터**가 된다.

---

### 10.3 MVP 이후 — 파이프라인 품질 개선

MVP 구현 후 실제 사용 흐름 또는 추가 평가에서 문제가 확인되면 파이프라인 개선을 다시 진행한다.

우선순위는 실제 발생한 문제에 따라 결정한다.

#### Stage 2 category accuracy

Stage 2의 역할은 Stage 1에서 추출된 후보에 의미 카테고리를 부여하는 것이다.

예:

```text
라떼 → FOOD
카페 → PLACE
자전거 → ACTIVITY
강아지 → ANIMAL
친구 → PERSON
```

이후 코드에서 해당 category를 기준으로 KEEP / DROP 여부를 결정한다.

따라서 다음과 같은 오분류는 단순히 category 이름이 잘못되는 데서 끝나지 않는다.

```text
ANIMAL → PERSON
```

이 경우 실제 수집 가능한 후보가 DROP 카테고리로 분류되어 뒤 단계에 도달하지 못할 수 있다.

MVP 이후 category 기반 기능이나 회고 기능에서 실제 문제가 발생한다면 Stage 2 accuracy 개선을 진행한다.

이때는 이미 prompt-only 수정에서 다른 category 경계의 회귀가 발생한 경험이 있으므로, 단순 규칙 추가보다는 별도의 supervised fine-tuning / QLoRA 실험을 검토한다.

---

### 10.4 ACTIVITY와 대표 오브젝트 관계 모델링

Final Selector 분석을 통해 다음 두 종류의 변환이 존재한다는 것을 확인했다.

```text
좋은 변환
뜨개질 → 목도리
도예 → 머그컵
피아노 연주 → 피아노

나쁜 변환
게임 → 스테이지
독서 → 챕터
등산 → 정상
서핑 → 파도
```

따라서 향후에는 단순 category 외에 후보가 기억에서 어떤 역할을 하는지 표현하는 개념이 필요할 수 있다.

예:

```text
semantic category
FOOD / PLACE / OBJECT / ACTIVITY ...

memory role
CORE
REPRESENTATIVE_OBJECT
CONTEXT
BACKGROUND
```

예를 들어:

```text
"도예공방에서 도예를 하고 머그컵을 만들었다"

도예공방 → PLACE / CONTEXT
도예     → ACTIVITY / CORE
머그컵   → OBJECT / REPRESENTATIVE_OBJECT
```

이 구조가 필요하다는 것이 실제 MVP 사용 과정에서도 확인되면 별도 모델링을 진행한다.

---

### 10.5 PLACE의 역할 분리 검토

현재 Final Selector는 장소를 배경으로 판단해 제거하는 경향이 있다.

그러나 장소는 두 종류로 나뉜다.

```text
단순 배경
공원, 테라스 등

경험을 정의하는 장소
아쿠아리움, 미술관, 공항, 항구 등
```

향후 회고 기능이나 지도/장소 기반 컬렉션 기능이 필요해진다면 PLACE를 최종 collectible 여부만으로 판단하지 않고 **기억의 context metadata로 별도 보존하는 구조**도 검토할 수 있다.

---

## 11. 최종 로드맵

현재 단계의 우선순위는 다음과 같다.

```text
Final Selector v0.5.2 freeze
        ↓
Happy-Hunt MVP 앱 구현
        ↓
Stage 2 category accuracy 개선
        ↓
ACTIVITY ↔ 대표 오브젝트 관계 모델링
        ↓
PLACE context / collectible 역할 분리 검토
```

즉 현재 POC의 목적은 **완벽한 아이템 추출 모델을 만드는 것**이 아니라,

> **실제 제품에 적용할 수 있을 정도로 후보 품질을 확보하고, 이후 개선이 필요한 문제를 구체적으로 식별하는 것**

으로 정의한다.

500개 검증을 통해 이 기준을 충족했다고 판단하므로, **파이프라인 추가 튜닝을 일단 중단하고 MVP 구현 단계로 이동한다.**
